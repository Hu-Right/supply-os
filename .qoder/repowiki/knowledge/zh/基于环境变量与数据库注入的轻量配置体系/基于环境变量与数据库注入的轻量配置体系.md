本仓库采用纯环境变量加运行时数据库注入的极简配置模式，没有引入集中式配置中心或配置文件。所有运行期参数通过 process.env 直接读取，并在启动时由 server.ts 从 MySQL 动态覆盖。

使用的框架与工具：
- dotenv：已声明为依赖，但当前代码中未显式调用 dotenv.config()，实际加载由运行环境在进程启动前注入。
- Express + Vite 单进程：后端 Express 与前端 Vite dev server 共用一个 Node 进程，配置入口集中在 server.ts。
- MySQL2 连接池：数据库连接参数硬编码在 server.ts 中，未走环境变量。

关键文件与位置：
- .env.example：仅列出 GEMINI_API_KEY、APP_URL 两个示例变量，作为对外暴露的配置清单。
- vite.config.ts：Vite 构建/开发配置，通过 DISABLE_HMR 控制 HMR 开关，通过 allowedHosts 允许外部域名访问。
- server.ts：唯一配置汇聚点——支付模式、第三方密钥、Gemini API Key、数据库连接等全部在此处读取并可能覆写。
- src/payment/PaymentService.ts：前端侧也直接读 ALIPAY_*、WECHAT_* 等环境变量以构造支付客户端。

架构与约定：
分层加载顺序：1) 平台注入的环境变量；2) hydratePaymentEnvFromDb 在启动时查询 crm_payment_provider_configs，将支付宝/微信配置写入 process.env，覆盖同名变量；3) 业务模块再统一从 process.env 取值。
运行时特性开关：PAYMENT_MODE=live|mock 决定支付走真实通道还是 MockProvider；NODE_ENV !== 'production' 用于调试分支。
数据库即配置源：支付提供商的 app_id、notify_url、public/private key_ref 等敏感配置持久化在 crm_payment_provider_configs，支持多 provider 多 mode 并存并通过 is_active 选择生效项。
缺失检测：getPaymentRuntimeConfig 汇总各 provider 是否完整配置，返回 configured/missing_env 供上层 UI 展示。

开发者应遵循的规则：
新增配置项：优先以 process.env.XXX 形式在 server.ts 顶部集中声明，必要时补充到 .env.example 注释说明。
敏感信息：不要硬编码到源码；若需持久化，使用 crm_payment_provider_configs 表并通过 hydratePaymentEnvFromDb 注入。
前后端一致性：前端 src/payment/PaymentService.ts 同样依赖 ALIPAY_*、WECHAT_* 环境变量，新增变量需同时更新前后端。
避免散乱读取：不要在每个路由里重复拼凑配置，统一由 getPaymentRuntimeConfig 或类似函数聚合后分发。
数据库连接参数：当前硬编码于 server.ts 的 mysql2.createPool({...})，如需可配置化，建议迁移至环境变量并保持与现有 ensureProcurementSchema 风格一致。
