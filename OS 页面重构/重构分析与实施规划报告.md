### 1.2 文档非视觉类要求（来自 OS 官网全模块重构规划.docx）

#### A. 数据质量规则（第 8 节）— 硬性要求

| 问题类型 | 前端表现 | 后台动作 |
|---------|---------|---------|
| 截止日期异常 (如 2126 年) | 不展示/标记待核验 | 超出合理范围自动拦截 |
| 标题过长/重复 | 摘要化显示，保留原文 | 相似度去重 + 来源优先级 |
| 金额缺失 | 显示"未公开"而非 0 | 空值与 0 严格区分 |
| 来源未知 | 不进入精选/推荐 | 必须有 `source_url/source_name` |
| 附件不可用 | 显示"原文无附件/抓取失败" | 定时重试 + 版本记录 |
| 供应商资质空白 | 字段整块隐藏 | 资料完整度不足时提示补充 |
| 认证状态 | 显示核验层级与日期 | 制定核验 SOP 和证据留档 |

#### B. SEO 架构（第 7 节）

**URL 结构**：
```
/tenders/country/kenya              → 国家长尾流量
/tenders/industry/medical-equipment → 行业长尾流量
/unspsc/42100000                    → 编码检索 + 机会聚合
/buyers/undp                        → 买家画像 + 中标历史
/awards/{id}                        → 历史情报
/suppliers/solar-energy             → 供应商行业页
/supplier/{slug}                    → 企业主页 SEO
/insights/{topic}                   → 知识内容获客
```

**技术规则**：
- 招标过期后**不要 404**，转为"已截止/归档"并推荐同类在招机会
- 中英文页面使用 `hreflang`
- Sitemap 按 `tenders/awards/suppliers/buyers/insights` 分片
- 标题模板：采购类型 + 产品/服务 + 国家 + 买家（避免同质化）
- 结构化数据只使用适用 schema，**不伪造 Rating/Review**

#### C. 实施优先级（第 9 节）— 90 天三阶段

| 阶段 | 时间 | 必须完成 | 商业目标 |
|------|------|---------|---------|
| **P0** | 0-30 天 | 首页、全球商机列表/详情、供应商库/企业主页、会员价格页；**修复日期/来源/空字段**；**CRM 退出公开导航** | 流量能注册、能解锁、能买会员 |
| **P1** | 31-60 天 | 中标情报、保存搜索/提醒、AI Bid/No-Bid、企业工作台、知识中心 SEO 模板 | 提高留存、专业版/企业版转化 |
| **P2** | 61-90 天 | RFQ、供应商询盘/对比、展厅地图、服务详情、课程闭环、API 入口 | 供应商侧变现 + 服务收入 + API |

#### D. P0 验收 KPI（第 9.1 节）

- 首页首屏：4-6 个实时规模数字 + 双搜索 + 2 个主要 CTA
- 采购列表：一屏至少 6 条，关键字段完整率 ≥ 95%
- 详情页：免费/会员/专业版权益分界清楚，**付费按钮不需要滚到底才能看到**
- 供应商库：展示"可检索/注册/认证"三个真实口径，**不再出现大片空字段**
- CRM：**匿名访客无法访问内部业务数据**
- 价格页：个人会员、企业版、API、单条包都能找到明确入口

#### E. 变现漏斗（第 6 节）

```
免费(搜索/摘要) → 注册(收藏/保存搜索) → 轻付费(¥199单条包)
→ 个人会员(¥799-4999/年) → 企业版(团队/工作台/顾问)
→ 项目服务(拆标/标书/代投) → 中标履约(谈判/保函/展厅)
→ 数据合作(API/年度授权)
```

#### F. 关键数据约束

- 所有计数**必须接真实后台**，新增量按过去 24 小时滚动计算，**禁止人工写死**
- 首页机会卡必须有：来源、更新时间、截止日期、附件状态
- 每条结果必须能追溯官方来源
- 不得显示"总可用解锁 0 条"这类负向提示，改成"升级后可解锁 X 条"

### 2.5 架构合规性分析

根据 ARCHITECTURE.md 的红线约束，重构需严格遵守：

```
✅ 规则1: src/lib 不 import features/app — 新后端端点放在 lib/services/ 下，不引用前端组件
✅ 规则2: src/core 不 import features/lib — 新 hooks 放在 features/ 下，通过 core/events 事件总线通信
✅ 规则3: src/features 不直接 import @/lib/** — 新页面通过 core/http 的 api()/apiCached() 走 HTTP
✅ 规则4: 服务端唯一入口 src/lib/** — 新 API 路由放在 src/app/api/ 下，委托 lib/services
```

**新增 feature module 建议**：
- `src/features/award-intelligence/` — 中标情报模块
- `src/features/rfq/` — RFQ 采购需求模块
- `src/features/supplier-profile/` — 供应商企业主页模块（或扩展现有 `supplier/`）

## 三、冲突点审查（20 个具体问题）

### 3.1 技术架构冲突（6 个）

| # | 冲突描述 | 影响范围 | 建议解决方案 | 优先级 |
|---|---------|---------|-------------|--------|
| **C1** | **CRM 公开访问 vs 文档要求"退出公开导航"** | 安全 | ✅ **已解决** — 添加鉴权守卫，未登录看介绍页 | P0 |
| **C2** | **SESSION ACTIVE STATUS 横幅 vs 文档明确禁止** | 全站视觉 | ✅ **已解决** — 删除徽标，保留标题和 CTA | P0 |
| **C3** | **导航容量上限 vs 新增模块** — 设计图 8 个导航项 + 首页=9 个，移动端溢出 | 全站导航 | 移动端采用底部 Tab Bar(5 项)+"更多"入口 | P0 |
| **C4** | **零图表库 vs 中标情报/CRM 数据可视化需求** — 代码库无任何图表依赖 | 模块 04/09 | 选用 `recharts`（~150KB gzipped，tree-shakable），仅相关页面懒加载 | P1 |
