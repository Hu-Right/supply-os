# 6. 旧品目树下线：改名 → 导出留底 → DROP，回滚靠副本而不是改回名字

日期: 2026-10-11
状态: 已接受

> **状态更新（2026-10-15）**：本文预告的终态已达成（旧树及退役名表均已物理 DROP，库内不在场）。一处口径需修正：「生效」段所述「三道 `--db` 门禁对缺席跨树项**明确打印跳过**」所依赖的缺表跳过分支，已在后续清理中删除（提交 `951b779c`，check-taxonomy 死分支）——跨树项不再「在场才执行」，其不变量已由树内自洽断言（BB1/BB4/BB5 + BB7）长期接管。表数口径以最新 `db/schema/baseline.sql` 头注为准。

## 结论

旧品目树 `crm_commodity_nodes` 的下线不是一条 `DROP TABLE`，而是三段式：**先 RENAME 成退役名（切断同名读取方，保留随时改回的能力）→ 全表导出为行定向可回灌的 SQL → 校验导出行数与表内行数一致后才 DROP**。回滚路径由「把名字改回来」变成「用副本重建原表名」，且这条路径在落刀前必须**实跑演练一次**才算成立。退役完成后由门禁 `BB13`（`scripts/gates/check-commodity-backbone.ts`）拦住中间态：库里出现 `crm_commodity_nodes_retired_*` 即红。

## 理由与权衡

新树 `crm_commodity_backbone`（159,429 行，L1 32 / L2 212 / L3 1,175 / L4 8,004 / L5 150,006）投产后，旧树 158,707 行的消费方需全部换源。仓库侧的引用可以用静态门禁证明为零（BB8：`src/**` 不得出现 `FROM/JOIN crm_commodity_nodes*`，正则带 `\w*` 后缀所以改名也拦得住），**但「仓库里没人读它」证明不了「库外没有读者」**——站外爬虫、后台任务、同事的临时查询都不在本仓库视野内。因此第一刀只做 RENAME（元数据操作，瞬时、不搬数据、可改回），观察期内出任何问题改名字即可止血。

真正决定流程形态的是取证时发现的一件事：旧树里有 **80 行 `source='self'` 自研延伸层**，旧码列恒 NULL、`gap_note` 全部只存在于这 80 行上（例如「粗叶子『半回路系统、DDPs和行政租赁传输方式的权益』承载 2583 条公告，官方四级无对应细分，需按线路通行权补偿拆细」）。设计稿明确把它们的用途记为**深层打标的细分线索**，而新树故意不接收（父品目 80/80 已被 L5 覆盖、self 行自身承载公告 0 条、一层只挂一个抽屉）。也就是说：**旧树整体已被替代，但这 80 行是唯一没被替代的内容**。所以「先导出」不是保守仪式，而是 DROP 的前置条件——导出脚本里硬性写成「导出行数 ≠ 表内行数」或「文件内找不到 self 行」就拒绝落刀。

代价：多一次 31.7 MB 导出与一轮演练，换来「不可逆动作实际可逆」。

## 能力边界（明确不解决的）

- 副本落在 `runtime/`（被 `.gitignore` 排除、无异地备份）。**库里没了、磁盘坏了就是真没了**——本 ADR 只保证落刀前那一刻副本完整且可回灌，不负责长期归档。长期保存需人工挪去有备份的位置。
- 回灌重建的是原表名 `crm_commodity_nodes`，与 `scripts/ops/commodity-legacy-rename.ts` 的改名前置互补：回灌后若仍要退役，需重新走「改名 → 落刀」，不能直接对原表名 DROP（drop 脚本按设计只收官退役名）。
- BB13 只拦中间态。库外的读取方如果真存在，它会在自己那边报错，门禁不会替它叫。

## 被否决的替代方案

- **直接 `DROP`（最快）**：不可逆，且那 80 行 `gap_note` 无处可寻——它是人工判断的输入，不是可重算的派生数据。
- **改名当终态、永远不 DROP**：退役名长期在场意味着「旧树到底有没有下线」变成口头知识；跨树断言（BB2/BB3/BB6、CG5、check-taxonomy C 段）会一直挂在「在场才执行」的分支上，谁也说不清它们还守的是什么。
- **先把 `gap_note` 搬进新树再 DROP**：新树的边界是「一张表装五级骨架，业务层故意无旧字典键」，塞入一层只挂一个子、且召不回任何公告的空抽屉，代价是 `code` 列宽扩容 + 「五级」契约改六级 + BB1/BB5 重写。换回的是一层空抽屉，所以不做。
- **把退役脚本纳入版本控制**：`scripts/ops/` 由 `check-gitignore-consistency.mjs` 在 lint/CI 强制不入库（一次性连库脚本），强行 `git add -f` 会同时踩 R1 隐身文件与 R2 不应被跟踪两条红线。沉淀进仓库的形式是**不变量（BB13）**，不是脚本本身。

## 生效与失效条件

生效：库里既无 `crm_commodity_nodes` 也无 `crm_commodity_nodes_retired_*`；`baseline.sql` 由 dump 脚本重导后为 97 张表；三道 `--db` 门禁对缺席的跨树项**明确打印跳过**（跳过不等于通过，接手的是 BB1/BB4/BB5 树内自洽 + BB7 逐码对树）。

已验的往返保真：回灌后跨树断言重跑全部成立（check-taxonomy 该项一次都没跳过、BB1~BB11 全绿且「原树 158,707 行未动」是真跑出来的），两次导出的数据段 md5 逐字节相同。

失效：若有人为「兼容」重新建出旧树同名表，或把退役名长期留着不动，BB13 会直接红——这条断言存在的意义就是让「退役」不允许停留在口头。
