# 7. 宽表派生列由构建方在同一次写入里算出，且线上只允许一个写入方

日期: 2026-10-11
状态: 已接受（含一项未完成的整改）

## 结论

宽表任何**派生列**（由其它表的码集合换算出来的列，如 `backbone_path` / `precise_backbone_path`）必须由 `buildWideRow` 计算、由 `upsertWideRows` 与业务列**同一批**写入；不允许另起定时任务、人工脚本或"同步收尾"来补列。同时，运行中的构建产物只能有一个：任何一份 `upsertWideRows` 列清单与 `src` 现状不一致的进程，都会持续生产缺列的行。

这是 ADR-0002（宽表单一写入者 + 源指纹）的补集。0002 自己写明边界："若宽表内容被绕过 `upsertWideRows` 的第三方**改坏**，存盘指纹仍与输入一致，检测不到"。本轮踩到的是边界之外的另一类事故：第三方不是改坏，而是**少写一列**——指纹仍然相等，门禁却查得出（BB7 要求"挂了码必填"），而 0002 的指纹机制对它完全无感。

## 理由与权衡

`backbone_path` 上线后，实测发现线上同步链路（`search-sync/wide-row-builder.ts`）不写任何品目派生列，全靠 ops 脚本算 ⇒ 新公告进来该列必为 NULL，五级下拉永远筛不到它。当时全库"有码却无归属"仍是 0 条——**因为回填之后还没有新行进来**，缺陷在数据上不可见。这类"沉默的正确性缺口"只能靠两条抓手：门禁闭合断言 + 把列并入构建方的写入路径。

修复位置为什么不是"同步任务收尾"：① `scripts/tools/daily-sync.cjs` 已于 2026-09-22 停用自动运行（逻辑迁入 `search-sync/crawler-sync.ts` + instrumentation），往它身上挂收尾等于挂在不再被调用的脚本上；② ADR-0002 的红线（`src/lib/**` 不得出现 `UPDATE crm_notice_search`，由 `check:wide-ssot` 强制）封死了"另起一个任务补列"这条路 ⇒ **修复方必须就是构建方**。

做法与代价（全部实测）：新增 `commodity/backbone-cache.ts`（进程内 TTL 60 分钟缓存整棵树，换算口径仍只在 `commodity/backbone-path.ts` 一份），行构建时一起算出归属。载入 15.4 s / 常驻堆 +71.3 MB；500 行批次含取码 SQL 共 271 ms；最重一条公告（5,091 个码）12 ms。指纹不含该列 ⇒ 此次改动不会引发 60 万行全表重写。

"第二个写入方"的代价随后被实测坐实：停掉那份旧构建（`next start`，构建时间早于列清单变更）后，门禁立刻报出 **BB7 有 117 条公告挂了码却 `backbone_path` 为空** + **BB10 有 30/1,210 行列值过期**。补算：`--incremental` 写 117 行，随后一次全量 `--only-changed` 扫 606,198 行报**写入 0 / 同值跳过 353,875 / miss 0**，两条断言转绿。

口径变更后的存量刷新同样有硬数据：族级落点从"一律中类"升级为"最深可证实唯一"后，全量 dry 报 **40,909 行待写（有码行的 11.6%）**；写前方向验（分 6 段均匀抽 3,000 行）为同值 2,745 / 只变深 255 / **脱离原链 0 / 反而变浅 0 / 丢掉原码 0**。刷新必须用 `--only-changed`（只写重算值≠现值的行），因为宽表 `updated_at` 带 `ON UPDATE CURRENT_TIMESTAMP`，而 Meili 增量同步恰好按 `updated_at ≥ NOW()-10min`（每轮 2000 行）取数 ⇒ 裸重写 35 万行等于让 35 万文档白白重索引。

## 能力边界（明确不解决的）

- 构建方算列依赖进程内的树缓存。**首次载入就失败**（库里没树 / 连不上）时该列写 NULL 并告警，不做任何"假装算得出"的兜底；缺位由 BB7 点名。刷新失败则沿用旧索引（陈旧但仍正确）。
- 本 ADR 不覆盖"读时计算"路线：若将来派生列不再落库而改为查询期换算，约束点从写入侧移到筛选侧性能。

## 被否决的替代方案

- **定时任务 / 同步收尾补列**：违反红线 #6，等于重新引入第二个作者；0002 已因同样理由否决过"逐处对齐 SQL"。
- **`--only-missing` 式增量补漏**：只补 NULL，看不见"已有值但码变了 / 口径变了"的行——本轮那 30 行列值过期正是这种形状。
- **裸全量重写刷新**：幂等但无差别，把 35 万行 `updated_at` 一起顶起来，连带 Meili 全量重索引（见上）。
- **给 `precise_backbone_path` 也加个缓存双写**：会造出口径的第二份实现，违反"换算只允许一处"。

## 生效与失效条件

生效需同时满足：

1. 每个宽表派生列都出现在 `buildWideRow` 的产出与 `upsertWideRows` 的列清单里，且两者同批；
2. 对应门禁断言是**双向闭合**（有码必填、无码必空，BB7 形状）；
3. `src/lib/**` 无 `UPDATE crm_notice_search`（`check:wide-ssot`）；
4. 运行中的构建产物只有一个。

**当前第 1、2 条存在一项已知的未完成整改**：`precise_backbone_path` 在 `src` 里没有任何写入方（只有 ops 脚本 `--column precise_backbone_path` 灌它），而门禁 BB11 取数用 `WHERE precise_backbone_path IS NOT NULL AND <> ''`——**单向对拍看不见"该填却没填"**。所以这一列现在能对齐（1,049 条差异 0）只因为它被人工灌过一轮，新进来的 approved 候选码会静默留 NULL。补齐方式即本 ADR 的既有做法：并入 `buildWideRow`，并把 BB11 改成闭合断言。

失效：若某天宽表改为事件驱动（outbox/CDC）重建，"构建方算列"仍成立，但"指纹不含派生列"的取舍需要重估。
