# 13. 段→大类允许常量兜底，换不出的深码不上浮、列值清 NULL（品目树重建后的换算收口）

状态: 已接受（2026-10-12 已在生产执行）

## 背景

2026-10-12 11:37，生产 `crm_commodity_backbone` 被 TRUNCATE 重灌为 82,737 行（此前 ADR-0010 记录的口径是 159,429），**85 段（医疗服务）的 L4 行整段消失**。ADR-0009 把「段→大类」的权威从归属表改成了「从骨架 L4 行的 `group_code` 反推」，于是这一段的换算链直接断掉：

- 公告↔旧码桥表的 13,238 个去重码里 **166 个换不出任何节点**（段级 1 / 族级 16 / 类级 36 / 品目级 113）；
- 涉及 6,589 条公告，其中 **4,604 条身上的码全部换不出**，按 `ACTIVE_NOTICE_WHERE` 口径仍有 **958 条活跃**；
- 门禁侧的投影：BB7 抽样「146 个列内码在树里不存在」、BB10「重算差异 39/1313」、BB3「可反推段数 57≠58」。

`backbone_path` 是派生列，它的正确性依赖「树是权威」。树一动，这一列就成批过期——而当时列值里挂着的是一批**树上已不存在的节点码**：等值筛能命中它们，前端点进去是无名节点。

## 结论

用户拍板：**一切以当前的品目树为准**，并在两个可执行口径中选乙。

1. **段映射 = 树反推优先 + `COMMODITY_GROUPS` 常量兜底**。树没推出某一段时，用常量的段→大类口径指到该大类在树上真实存在的那一行 L1（不是造码，也不是拿公告挂一个不相干的宽节点）；常量不得覆盖树已有的结论。
2. **族/类/品目级深码一律不上浮**。`backbone-path` 对「8 位全有效却查无品目」继续返回 null，维持原取舍「不拿公告硬挂更宽的节点」。
3. 换不出的公告，由回填把 `backbone_path` 清成 **NULL**（脚本口 `--unmapable-null`），而不是留着指向不存在节点的旧值。
4. 门禁 BB7 的「有码必填」随之收紧为「**可算必填**」：拿同一份纯函数对当前树重算，算得出却没填的才是回填缺位；全码换不出只报数不计红。

## 判据（落刀前实测，均为只读探针）

- **兜底可行性**：166 个换不出的码，其 2 位段前缀在 `COMMODITY_GROUPS` 里全部有归属，且树 L1 恰好 32 个大类各一行（无一对多、无缺失）⇒ 166/166 能指到一个真实树节点。
- **实际只救回段级那 1 个码**（`85000000`），但它覆盖 **1,461 条公告（活跃 321）**；其余 165 个是深码，按第 2 条不救，剩 **3,143 条真空（活跃 637）**。
- **dry 与 apply 逐位一致**：扫 608,004 行 / 有码 359,348 / 写入 **4,854**（清 NULL 3,116 + 改粗 1,738）/ 同值跳过 354,467 / 最长值 85,141 字符（上限 1,000,000）。清列前该列已填 359,496 行。
- **写前留底**：`crm_notice_backbone_backup_20261012` 4,854 行原值（其中 23 行原本为 NULL，正是 BB7 抓出的「可算却未填」）。

## 代价与能力边界（明确不解决的）

- **637 条活跃公告的分类被清空**（总 3,143 条）。这是「精度优先」的直接账单，不是可以事后忽略的偏差。它们同时是 **AI 补码的第一优先候选集**——BB7 报数里「全码换不出 N 条」这一行就是该候选集的实时计数。
- 被清掉的列值**无法从当前树重算回来**（重算结果就是 NULL），所以留底表是唯一回滚物：回滚 = `UPDATE crm_notice_search w JOIN <backup> b ON b.id=w.id SET w.backbone_path=b.backbone_path`。确认不回滚后 DROP；**DROP 之前不要重导 `baseline.sql`**，否则这张临时表和同时在途的 `crm_commodity_backbone__new` 都会被写进跟踪文件。
- **倒排镜像（ADR-0010）的主循环看不见被清空的行**：它从「`backbone_path` 非空」出发，所以那 3,116 条公告的镜像行不会自己消失。本次实测留下 13,584 行残行 / 3,115 公告，由 BB14 的「行数 = 源 token 数」与「残行 = 0」两条抓出（这两条断言是本次唯一发现该缺陷的途径）。已给脚本补反向通道 `--purge-orphans`（配 `--skip-mirror` 可只清不重镜）。
- **BB3「可反推段数=57，应为 58」保持红**，不降为 WARN：它守的是「树必须覆盖全部常量段」，降级等于宣布树可以缺段。若 85 段由在途的 G11 重排/融合树补回，这条自然转绿，常量兜底会因「树优先」自动让位。
- 留底/镜像表的**列形制必须抄 `information_schema`**，不许手写：本次留底表列被写成 `TEXT`（65,535 字节），而源列是 `MEDIUMTEXT`，跑到一行 136,803 字符时 `ER_DATA_TOO_LONG` 中断。因「先留底再改」的顺序，中断那批一行未写，可安全 `--resume`。

## 被否决的替代方案

- **补树**（把 85 段缺的 20 个族造回骨架）：零代价救回全部 4,604 条，但树的形状是 `rehoming-g11` / 融合树那条在途线的产物，不能由数据治理侧替它决定。
- **上浮第五档**（深码逐级退到树上最近的真实祖先：类→族→段→大类）：可救 3,445 条（活跃 686），且目标节点确实存在；但它正面违反 `backbone-path` 里那条为精度而设的取舍，还要连改 BB9/BB10 的落点口径。属「精度换覆盖」的独立决定，已否。
- **不改任何规则、直接重跑回填**：4,604 条（活跃 958）全清，代价最大，且旧列值会作为鬼魂长期留在库里（默认「批内有 miss 就停手」的保守语义等于什么都不改）。
- **指望 AI 直出节点码顺手覆盖存量**：新链路（`crm_notice_attribution_nodes`，R2/R3）根本不经过 `match()`，救不了存量换算断点；存量必须先按本 ADR 收口，否则 R2 切读那一刻有 3,143 条公告无落点可吃。

## 生效与失效条件

- 生效：2026-10-12 生产已落地（宽表 4,854 行改写 + 倒排 35,413 行重镜 + 13,584 行残行清理；门禁 BB14 回绿，BB10 差异 39 → 6，BB7「列内码不在树」归零）。
- **BB7「可算必填」与本口径绑定**：改 `match()` 的兜底范围必须同时复核 BB7 的措辞，反之亦然。
- 线上应用若仍跑旧构建，BB10 会报出「新公告由旧规则写入」的分叉（现测 6/1313），它随本次代码发布自然收敛，不是数据坏。
- 失效：旧字典码→节点码的 legacy 换算随 R3/R4 退役后，第 1~3 条只对历史数据有意义，届时连同 `backbone-path` 的旧字典分支一起删除；第 4 条（BB7 的「可算」语义）长期有效。
