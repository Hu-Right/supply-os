# ADR-0004: 撤销"企业信息 ↔ 供应商资源库"身份互斥（改为档位/数据驱动）

- 状态：已接受（Accepted）
- 日期：2026-09-21
- 取代：ADR-0001（企业信息与供应商资源库互斥、先用先占、身份不可转换）——本 ADR 生效即**废止** ADR-0001
- 关联：会员权益体系 V2（《云境产品服务权益报价表_260921_V2》）、`lib/services/benefit-matrix`（门控 SSOT）

## 背景

ADR-0001 将"绑定企业"与"供应商资源库（外贸员身份）"设为二选一、先用先占、不可转换，并在服务端强制：
- `POST/GET /api/user/supplier-pool`：已绑定企业 → 拒绝 / 返回空；
- `POST /api/notices/[id]/ai-match`：已绑定企业 → 403（智能匹配仅外贸员可用）；
- `POST /api/user/enterprise`：资源库非空 → 403。

产品复核（结合 V2 报价表）发现该互斥存在三重问题：
1. 与 V2 立身原则"身份与额度/功能分离"相冲突——把功能可用性重新焊回身份；
2. 误伤"既绑定企业、又代理多家工厂"的真实外贸场景（公司也可能有工厂池，想用智能匹配挑厂）；
3. 报价表各档并不把"①智能匹配"列为按身份区分的卖点，用身份去卡它无收入/产品依据。

①智能匹配（从用户资源库推荐 Top N 供应商）与②AI 适配评分（评单一企业自身适配度）实为同一套"供应商 × 公告"评估能力的两种用法，本应共存而非互斥。

## 决策

1. **解除身份互斥**：账号可同时拥有企业主体与供应商资源库；`supplier-pool` GET/POST、`ai-match` POST、`enterprise` POST 不再按 `hasEnterpriseBinding`/`hasSupplierPool` 拦截。`lib/services/identity.ts`（仅服务互斥）随之删除。
2. **①②改为按"档位 + 数据"放行**：
   - ①智能匹配：仍受"解锁校验 + `benefit_rank ≥ 专业版(3)`（`hasFeature('ai_score')`）"约束；空资源库时前端引导去添加，不做身份封禁。
   - ②适配评分：仅当账号有企业主体（`hasSupplier`）时展示（否则无评估对象）。
   - 详情页「AI 适配评分」Tab 由"按身份二选一渲染"改为**两卡同页共存**，各自按上述条件显隐。
3. **settings 信息架构**：企业信息、供应商资源库两项导航**常显**（去掉 `exclusive` 互斥过滤），移除"身份不可转换"警告与企业↔资源库互斥拒绝屏。

## 后果

- 正面：能力不再因身份被凭空剥夺；与企业也能建工厂池的现实场景一致；与 V2"身份/额度分离"及报价表对齐；门控判定继续收敛于 `benefit-matrix` 单一事实源。
- 代价：企业用户可产生资源库与匹配数据，需确保匹配/评分的额度计量沿用既有用量口径（不受影响，仍走 entitlement）。
- 文案：`supplierPoolEnterpriseDenied`、`enterprisePoolDenied`、`settingsIdentityWarning` 等键在六语包中暂保留但已无引用（不破 i18n 键一致性），后续本地化专轮再清。

## 替代方案（已否决）

- 仅放开 ai-match 一处、保留其余互斥：①对企业仍不可用（无库可匹配），不达目的，否决。
- 引入显式 `user_type` 枚举强绑角色：与 V2 解耦方向相悖，成本大，否决。
