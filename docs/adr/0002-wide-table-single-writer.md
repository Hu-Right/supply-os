# 2. 宽表收敛为单一写入者（源指纹），而非逐处对齐对账 SQL

日期: 2026-09-20
状态: 已接受

## 结论

`crm_notice_search` 的业务内容列与一致性指纹 `sync_src_hash` 只由 `buildWideRow → upsertWideRows` 写入（二者取自同一次 SELECT 快照）；对账层退化为「只检测、返回待重建 id」；跨层口径（描述来源表达式、截断长度、译文 `model`、合格机会谓词）抽为 `lib/utils/` 常量单一出口；并由 `scripts/check-wide-table-ssot.mjs` 把该标准变成 CI 硬门禁（ARCHITECTURE.md 红线 #6）。

## 理由与权衡

宽表同时被「构建路径」与 5 段手写 `UPDATE` 修复路径写入，两份口径各自演进必然分叉。现网实测（本地镜像库，宽表 462,018 行）已产生：**8,367 行**描述被对账改回主表值而详情页展示机会表值（搜索摘要与详情页长期不一致）、4,082 行会被反复误判、精选公告人工拆解摘要遭机器译文覆盖、同语言直通判定值写成全库不存在的 `'skip-same-lang'` 导致描述恒空、内容漂移对账因批次算法只扫 id ≤ 2000 而在生产几乎不生效。

逐处对齐 SQL 能止住当下症状，但只要口径仍存两处，任一侧改动就会复发。指纹方案把「宽表是否落后于输入」变成一次可比较的哈希，从结构上取消第二个作者：修复方即构建方 ⇒ 重建后必然相等 ⇒ 收敛性可被自动断言，而非靠人肉比对两处 SQL。

## 能力边界（明确不解决的）

- 指纹只覆盖**输入侧变更**。若宽表内容被绕过 `upsertWideRows` 的第三方改坏，存盘指纹仍与输入一致，检测不到。该完整性由红线 #6 + 门禁保证；对历史存疑时把 `sync_src_hash` 批量置 `''` 即强制全表重导（首次上线即因新列默认 `''` 自动完成一次全表重建，顺带修掉上述 8,367 行）。
- `crm_agency_aliases` 与 UNSPSC 字典树自身的变更不进入指纹（全表级维度，构建侧有 10 分钟缓存 TTL），需刷新走 `requestIndexRebuild`。

## 被否决的替代方案

- **逐处修正 5 段对账 UPDATE 的表达式**：改动最小、当天可上，但口径仍存两处，属"下一次必然复发"的修法。
- **Outbox / CDC 事件表彻底摆脱 id 水位**：最干净，但要求站外审核后台改为写事件表；该后台不在本仓库，跨系统协调成本与本轮收益不匹配。若将来出现「对账延迟造成业务事故」的真实案例，由 outbox 消费取代本方案的轮转对账。
- **把 `rfq_status` 冗余进宽表并在查询侧过滤不可见行**：可避免发布/撤回的删增震荡，但代价是未发布内容进入索引与 SSR 面（合规风险），且每个消费方都要带该过滤条件。

## 生效与失效条件

生效：`src/lib/**` 无 `UPDATE crm_notice_search`（门禁保证）；连续两轮全量对账变更数为 0（测试断言）。
失效：若别名/字典变更成为高频事件，"不进指纹"的边界不再成立，需把维度版本纳入指纹或改为定时全量重建；若站外后台可改造，则轮转对账应被 outbox 取代。
