# 3. 数据库结构变更采用影子表蓝绿切换（两阶段 · 人工闸口）

日期: 2026-09-21
状态: 已接受

## 结论

- **分级启用**：高风险结构变更（改列类型、改字符集/排序规则、重建表、生成列表达式变更、需回填/改写大量既有行、拆/合列）**必须**走「影子表」流程；低风险纯增量（新增可空列、加/删二级索引等 MySQL 8 可 INSTANT/INPLACE 完成者）保留现有直接 `ALTER`。
- **影子表流程** = 复制结构 → 改结构 → 分批回填 → 校验 →（人工测试）→ 冻结外部同步 → 补增量 → 原子 `RENAME` 切换 → 保留旧表可回滚。
- **两阶段 + 人工闸口**：阶段一只创建 `<原表>__new`，**旧表不改名、继续跑生产**；测试/预览指向新表；**阶段二经人工确认完善后才彻底换表**。切换绝不与建表合并在同一自动迁移里完成。

## 命名约定

- 影子表：`<原表>__new`
- 切换后保留的旧表：`<原表>__old_<YYYYMMDD 或目标版本>`

## 标准流程

### 阶段一（迁移可自动执行，全程不触碰线上读路径）

1. `CREATE TABLE <t>__new LIKE <t>;`（带列、索引、AUTO_INCREMENT 定义、字符集）
2. 在 `<t>__new` 上完成结构变更。
3. **结构自检**：列/索引/生成列/字符集/排序规则符合预期。
4. **分批回填**：`INSERT INTO <t>__new (...) SELECT ... FROM <t> ...`，按 id 分段（如每批 5000），避免单条大事务、长时锁与 undo 膨胀。
5. **数据校验**：行数一致 + 抽样比对（必要时 checksum）。
6. **到此为止**：不 `RENAME`、不改旧表名 → 旧表继续服务生产。

### 测试 / 评审（人工）

- 测试与预览数据源指向 `<t>__new`，不读写线上旧表。
- 人工确认「完善」后，才进入阶段二。

### 阶段二（人工确认后才执行；独立迁移或人工运行脚本）

1. **冻结外部同步**（daily-sync / 站外 CRM 写入）——见「外部实时写表」约束。
2. **补增量**：把阶段一回填之后旧表新增/变更的行同步进 `<t>__new`（按 `updated_at > 水位线` 或 id 水位）。
3. **原子切换**：`RENAME TABLE <t> TO <t>__old_<ver>, <t>__new TO <t>;`（RENAME 原子且瞬时，即秒级切换）。
4. 保留 `<t>__old`，验证稳定后择期人工清理（默认人工确认后再删）。
5. 解冻外部同步。

## 分级判据

- **走影子表**：变更会让既有行需要重写，或结构写错会当场污染线上数据（改类型、重建、生成列表达式变更、大批量回填、拆/合列、改字符集）。
- **走 INSTANT/INPLACE ALTER**：新增可空列、加/删二级索引等 8.0 可原地完成者。
- 一句话边界：拿不准会不会"重写既有行"的，按影子表处理。

## 理由与权衡

现状是迁移直接在原表 `ALTER` + 回填，结构错误会当场污染生产（本轮 089 迁移给生成列 `deadline_sec` 赋值即导致启动中断）。影子表把"改结构"与"动线上数据"解耦：结构先在新表验证通过才回填；回填期间旧表仍是可信生产源；切换与回滚都是一次原子 `RENAME`。代价是临时约 2× 磁盘、一次全量拷贝、两阶段需人工闸口与外部同步冻结窗口——因此只对高风险变更启用，低风险增量不强推。

## 能力边界 / 必须注意

- **外部实时写表**：`supplier` / `crm_bid_notices` / `crm_bid_opportunities` 等由 CRM 与 daily-sync 实时写入。阶段一回填到阶段二切换之间旧表会产生增量，**必须在切换窗口冻结同步并补增量**，否则切换丢写。app 自有表（`crm_users` 等）无此问题。
- **外键**：`CREATE TABLE LIKE` 会复制外键定义；其它表按名引用 `<t>` 的 FK 在切换后仍指向同名新表，逻辑成立，但新表自身复制的同名约束可能与子表既有约束冲突，切换前须核对/重命名。
- **自增值**：确认 `<t>__new` 的 `AUTO_INCREMENT` ≥ 旧表，避免切换后主键冲突。
- **触发器/事件**：`LIKE` 不复制触发器，旧表若有触发器需在新表手动重建。
- **幂等与版本追踪**：阶段一、阶段二各为独立迁移（或阶段二为人工脚本）；runner 仅在整体成功后记录版本；两阶段都必须可安全重跑。

## 被否决的替代方案

- **全部变更一律影子表**：低风险加列也要 2× 盘 + 全量拷贝，成本不划算 → 改为分级。
- **单个迁移内自动完成 build + swap**：违背人工闸口，未经确认就把新表切上生产 → 拆成两阶段。
- **引入 pt-online-schema-change / gh-ost**：成熟，但需额外运维依赖，且其触发器增量方案与本项目"冻结 daily-sync"策略重叠 → 先以仓库内 helper + 本 ADR 落地；未来出现高频在线大表重建需求再评估替换。

## 生效与失效条件

- 生效：新增高风险迁移均按本 ADR 产出阶段一 / 阶段二两个产物；`__new` / `__old` 命名一致；切换前外部同步冻结有记录。
- 失效 / 复审：若运维引入 gh-ost/pt-osc，或出现"冻结窗口不可接受"的高频在线切换需求，则由专业在线 DDL 工具承接本流程。
