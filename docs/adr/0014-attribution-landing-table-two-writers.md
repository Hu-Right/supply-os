# ADR-0014 公告归属事实源是落点表；该表有两个写入方，靠 source 契约而非改键约束

日期：2026-10-13
状态：已采纳（R1' 已于 2026-10-13 出口达成；契约的机器化断言已落地为**独立门禁 AS1~AS5**，非原拟的 BB15e；
另登记一项与本文第「被否」条冲突的现实发现，见结论 7）

## 背景

旧字典全面退役 v2（设计稿在 `docs/superpowers/specs/` 下，未入库）把 D1' 定为**物理零残留**：连 `crm_commodity_backbone` 的旧前缀列一起删。这一刀同时动掉两样一直被当作"权威"的东西：

1. **段→大类的反推路径**。ADR-0013 的口径是「树反推优先 + `COMMODITY_GROUPS` 常量兜底」，而"树反推"读的就是旧前缀列的 L4 六位前缀。列删掉后，常量**由兜底升为唯一来源**，BB3「可反推段数 = 58」这类判据从此无从校验。
2. **归属的独立重算能力**。`backbone_path` 一直是「8 位码 → 树」的派生列，任何人拿桥表加树就能重算一条公告为何落在此节点。退役后这条通道不存在，公告归属只能有一个事实源：`crm_notice_attribution_nodes`。

R1' 据此建表并从列值反推灌入存量（`source='legacy_tag'`），生产落地 **638,381 行 / 356,431 公告**，三条对账闸口全绿。随后门禁 BB15c 报出抽样差异，追查中撞见一件建表时不存在的事实：**这张表已经有第二个写入方**——并发的作业流正在把「同步公告里换不出节点的野码」按 UGT 标准分类后写入同一张表，`source='ai_content'`，配套 `crm_taxonomy_intake`（pending/resolved）队列（其语句痕迹：16:42:59 的 27 次 `INSERT INTO crm_notice_attribution_nodes` 写入 32 行，16:47:17 的 `DELETE ... WHERE source='ai_content'` 删 27 行）。

## 结论

1. **段映射常量为唯一来源**。`COMMODITY_GROUPS` 不再是 ADR-0013 意义上的"兜底"，而是段→大类的权威；「树优先」那半边随旧前缀列退役失效。BB3 判据相应改为「每个常量段都有 ≥1 个 L1 行携带其 `group_code`」。
2. **公告归属唯一事实源 = `crm_notice_attribution_nodes.node_code`（存最深落点，不存祖先链）**；`backbone_path` 继续是派生列，由 `pathOfLandingNodes()` 补全祖先、由宽表构建器唯一写入（ADR-0007 前提不废，只换输入）。
3. **两类 source 的性质不同，处置权不同**：`legacy_tag` 是从列值反推的**快照**，可整批重灌、无信息损失；`ai_content` 是判定产出的**事实**，换不回来。因此**禁止在正名表上做 `--drop-table` 回滚演练**（原 R1' 的回滚位作废），演练一律改影子表。
4. **唯一键不加 `source`，改用门禁守住分桶契约**。并发方的写入范围是「只瞄零落点公告」，而 `legacy_tag` 覆盖的是「有列值」的公告 ⇒ 两边按公告天然分桶，同一公告不会混两种 source。为一条已被契约挡住的冲突付一次生产 `ALTER` + 双方停写窗口是净亏。代价是契约没有库侧约束，所以**必须补机器断言**：已落地为独立门禁 `scripts/gates/check-attribution-ssot.ts`（原拟名 BB15e 即其 AS1：`GROUP BY notice_pk HAVING COUNT(DISTINCT source) > 1` 必须 0 行；另包含全量版的 AS2 快照、AS3 半写、AS4 断供、AS5 换源）。判据单一来源 `src/lib/services/commodity/attribution-contract.ts`，与门禁、灌入脚本、未来的增量镜像共用。
5. **BB15b / BB15d 的 source 分档：不是「尚未落地」，而是「已落地但口径相反」（2026-10-13 自己复算纠正本 ADR 初稿的错误陈述）**。
   本 ADR 初稿写「这两条住在并发方在途未提交的文件里 ⇒ 尚未落地」，去查 `HEAD` 的 `scripts/gates/check-commodity-backbone.ts`：
   BB15b（自连接判互为祖先）与 BB15d（「有落点无列值」计数即 `fail()`）**早已提交，且都没按 source 分档**。
   拿它们原 SQL 只读复算（`temp/probe210-bb15-split-by-source.ts`）：`BB15d 有落点无列值 = 163`，其中
   `legacy_tag 侧 = 0`、`非 legacy 侧 = 163` ⇒ **今天跑 `npm run check:backbone -- --db` 必 exit 1，而那 163 行全是对方的 ai 落点**；
   同一份数据上 `check-attribution-ssot` 全量 exit 0 —— **两个门禁对同一数据结论相反，这是现在的实况不是将来的风险**。
   （BB15b 今天还未误报：非 legacy 公告内的互为祖先对数实测 0；但 AI 一旦写入某 legacy 叶子的祖先就会误报，且该自连接
   在 60s 超时下跑不完全表，本身也是长查询风险。`check:backbone` 需显式 `--db` 才连库，所以无库的 CI 不受影响，受影响的是本地与发布前验证。）
   **口径约定**：R2' 验收以 `check-attribution-ssot` 全量 exit 0 为准；`BB15d` 的 legacy-only 分档与 `BB15b` 的同 source 分档
   列为限期整改项（它们在那个热文件里，本计划不动他人地面）。在两处口径合流之前，任何人拿 `check:backbone -- --db` 的红
   去当「落点表坏了」的证据都是错的。
6. **R2' 的出口判据按 source 拆**：`legacy_tag` 派生值必须逐条等于现列值（差异 0）；`ai_content` **允许**让列值从无到有——野码分类的目的就是补归属，"换源不改归属"这句原判据对它天然不成立。
7. **一项与本 ADR 第「被否」条冲突的现实发现（2026-10-13，待对方定）**：本计划评审在并发方的 `scripts/ops/notice-attribution-content-ai.ts` 与
   `notice-attribution-manual-anchor.ts` 里读到 `ON DUPLICATE KEY UPDATE ... source=VALUES(source)`——即本文已否决的“覆盖审计线”写法。
   它的危险不在公式而在时序：「只瞄零落点」的筛选在 **SELECT 时刻**，落笔在数次 LLM 调用之后 ⇒ 本计划灌完某公告的那一瞬间，它有权把 `legacy_tag`
   行原地改成 `ai_content`。这种形状 **AS1 抱不到**（要两源共在才红）、**AS4 也抱不到**（不是零落点）⇒ 存量归属被悄悄换源而门禁全绿。
   本 ADR 为此新增 **AS5** 兜住检测（公告只剩非 legacy 行、而列值声明的叶子无承载 ⇒ 红）；**真正的修法在写入侧**（落笔改 `INSERT IGNORE`、
   或写前复查一次、或双方共用 `GET_LOCK`），属对方的设计决策，本 ADR 只登记判据，不代改代码。
7b. **AS5 也有抱不到的残差（已写进单测钉住边界，不假装它能防）**：若 ODKU 只是把 legacy 行的
   `source/model/confidence/evidence_text` **原地改属性而节点码未变**，则列值声明的叶子仍被覆盖 ⇒ AS1~AS5 全绿。
   AS5 保住的是「归属没丢」，没保住的是「这条归属是谁说的」—— 后者就是本文否决 ODKU 时用的那条理由，它仍然存在，
   **只能靠写入侧不覆盖来防**。另：非 legacy 侧的脏列不判红，但已有 `stats.dirtyColumnNotices` 计数与文本出口（旧实现是静默 `continue`）。
7c. **除 `--drop-table` 之外还有第二条销毁通道（2026-10-13 终审发现，属既有代码）**：已提交的
   `scripts/tools/commodity-g11-rehome-cutover.ts` 的 `--cleanup` 会 `DELETE` 落点表行，**无 source 过滤、不经 `assertDroppable`**，
   且提示里把重灌 `backfill` 当恢复手段——对 `ai_content` 行那是假承诺（本文结论 3 明说换不回来）。
   本文第 3 条的硬闸只封住了它自己那条通道；该脚本列为已知风险，随 R6'/人工流程处理，运行前必须先加 source 过滤。

## 判据（2026-10-13 生产实测；本计划侧探针 `temp/probe199~203`、`probe205~206`，全量对拍见下）

- **落点表健康度**：638,381 行，全部 `legacy_tag`，`id` 用满 638,386 ⇒ 缺 5 行，缺号 `35/4325/5835/7470/11898` 与缺失落点一一对上：`725/UGT-0204020103`、`4728/UGT-0404030220`、`5072/UGT-0207020102`、`5113/UGT-0204020102`、`8701/UGT-0802010505`。
- **全量对拍**（356,431 条逐条，由**并发作业流**执行：`temp/probe204-r2-drydiff.ts` → `temp/probe204.out.json`；注意两个会话用了同一个编号 `probe204`，与本 ADR 引用的本计划侧 `probe204-replay-dup-pairs.ts` 不是同一个脚本）：`C1 有列值·无落点 = 0`、`C2 派生≠列值 = 5`、`C3 有落点·无列值 = 0` ⇒ 缺口就是这 5 行，不是系统性漂移。本 ADR 侧的等价证据是 `probe203` 的全表主键缺号扫描（同样 5 个）。
- **排除项**：列值未被重写（这些公告宽表行 `updated_at = 2026-10-13 10:28:04`，早于落点行的 `16:34:03`）；`crm_notice_search` 为 `PRIMARY(id)`、608,004 行无重复 id；`SHOW CREATE TABLE` 证实 `uk_notice_node(notice_pk,node_code)` 全码无前缀、无 CHECK、无触发器、无定时事件；按灌入脚本同口径回放前 20 批，批内与跨批重复对为 0；这 5 个码在表里的 294 个持有者全部名正言顺（挂错人 = 0）。
- **未查明——已于 2026-10-13 影子演练定性为「非必然」**：对同一批 6,000 条公告（`id ≤ 35712`）在全新空表上重跑同一段灌入代码，
  影子表 `crm_notice_attribution_nodes__drill` 产 **61,645 行**，正名表同区间只有 **61,640 行**；逐对差集「影子有、正名没有」**恰为那 5 对**
  （反向差集 0 行，该区间 `source <> 'legacy_tag'` 行数亦为 0）。⇒ 缺失**不是输入决定的**，也不是撞键占位；只能归给外部写入方在这张表上的动过痕迹。
  **具体哪条语句删的仍未确证**，本 ADR 不把它写成结论。取证脚本 `temp/probe209-drill-vs-real.ts`；影子表保留不删（它就是这条结论的证据）。
- **处置结果（R1' 出口）**：2026-10-13 20:53 以 `--apply --yes --limit-batches 12` 幂等补灌，**实插 5 行**；随后全量复扫
  `纯 legacy 一致 356431 = 列值公告数`，AS1/AS2/AS3/AS4/AS5 均为 0，exit 0。补灌时写前普查拍到 `ai_content` 行数已从 50 涨到 89（公告数 98）
  ⇒ 分桶契约在现网成立至今有机器证据。

## 代价与能力边界

- **常量写错无人拦住**：段映射只剩一条代码里的常量，旧前缀列删除后再无独立手段核对它。唯一防线是 BB3 的新措辞与 `commodity-groups.test.ts`。
- **归属不可独立验证**：一条公告当年为何落在此节点，只能信落点表的 `confidence / evidence_text / model` 三列（v2 规格 §6 第 4 条已作为明确接受的后果登记）。
- **分桶契约不再是软的（已机器化），但 AS5 抱住的形状仍依赖对方自觉**：AS1~AS5 已上线，任何一方混源会当场报红；
  而结论 7 的 ODKU 改写只在**全量扫描之间**才报 AS5（AS1 抱不到），所以它本质上仍是一条需对方修写法才能彻底关掉的红线。
- **增量镜像的候选谓词偏窄（2026-10-13 发现，交实现方定）**：`src/lib/services/commodity/attribution-mirror.ts` 用
  `NOT EXISTS (落点表里有该公告任意一行)` 选候选 ⇒ 只补「零落点」的公告。落点已有部分行的公告（列值后来因新码变长的情况）
  **永不会被回补**，正是那 5 行缺口的长期复现形态。候选谓词应为「列隐含落点 − 现有落点 ≠ ∅」，
  `attribution-contract.missingLandingPairs()` 就是它的现成判据。本 ADR 不替对方改文件，只登记判据。
- **落点表成为共享表**：任何 `--apply` 前须先 `SELECT source, COUNT(*) ... GROUP BY source` 并在 `runtime/` 登记写入窗口。
- **AI 触发权不在本链路上**：`ai_content` 的生产者带 `--scope` 体量预估（15,646 条零落点公告）且默认不调 API，放量与否由需求方逐次放行。

## 被否决的替代方案

- **`uk` 加 `source`（多来源共存）**：能彻底消除撞键，但同一节点两行会让 BB15b 跨 source 误报、读侧要额外定义"同节点两来源听谁的"，且需一次生产 `ALTER` + 双方停写。在分桶契约成立的前提下收益为零，已否；**若将来 AI 需要翻案存量节点，由 AS1 报红重新提出**。
- **唯一键不动、AI 改判走 `ON DUPLICATE KEY UPDATE`**：会把 `source/model/confidence` 覆盖掉，"哪些落点是可重算快照、哪些是不可重算事实"这条审计线当场消失，门禁分档也就无从写起。已否。**但 2026-10-13 实测对方的两个 ops 脚本确实在用 ODKU** ⇒ 这条否决在现实中已被越过，见结论 7；本节保留是为了说明：当时的否决理由今天看仍成立，只多了一个检测手段（AS5）。
- **停掉一方串行推进**：`ai_content` 是这张表里唯一产出新信息的一方，也是 v2 规格 D2' 的硬前置；停它换不到任何数据安全，只是把不可逆的那段进度按住。已否。
- **保留 `--drop-table` 正名回滚演练**：在共享表上演练等于拿别人的不可重算事实当道具。已否，改影子表。落地时比纪律更硬：`notice-attribution-ddl.ts` 的 `--drop-table` **按身份直接拒正名表**，不看普查内容——因为并发方有 `DELETE ... WHERE source='ai_content'` 类清理动作，普查与 DROP 之间存在「只剩 legacy_tag」的合法瞬间，拿“当下有数据”当安全依据就是赌 race。

## 生效与失效条件

- 生效：2026-10-13 起。落点表已在生产，第 3~6 条约束 R2'/R3' 的全部动作；第 1 条在旧前缀列删除那一批（R4'）才真正生效，删除前树反推仍是优先来源。
- **失效/升级**：若 AS1 首次报红（同一公告混了两种 source），本 ADR 第 4 条的前提不成立，必须回到"加 `source` 进唯一键"或"先删 legacy 再写 AI"，并另立 ADR 记录那次改判的口径。**若 AS5 首次报红**（归属被换源而无混源），则结论 7 的 ODKU 已从风险成为事实，优先改写入侧而不是改键。
- 连带：ADR-0013 第 1 条（树反推优先）随旧前缀列退役失效，其第 2~4 条（深码不上浮、换不出清 NULL、BB7「可算必填」）继续有效。
