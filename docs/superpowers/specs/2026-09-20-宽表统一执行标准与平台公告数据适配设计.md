## 1. 根因

`crm_notice_search` 存在**两个作者**：

1. 构建路径：`buildWideRow` → `upsertWideRows`（`wide-row-builder.ts`）
2. 修复路径：`wide-row-reconcile.ts` 内 5 个手写 `UPDATE crm_notice_search SET ...`

两条路径各自维护一份字段口径，任何一侧演进都会让另一侧失真。用户提出的四类症状（编号前缀、字段映射、描述来源、翻译缓存）都是这个结构问题的**派生现象**，不是独立缺陷。因此本轮不逐条打补丁，而是把宽表收敛为单一作者，并把口径抽成常量级单一事实源。

> 取证修正（2026-09-20）：本档初稿把 D4 描述为“每 5 分钟震荡一次、永不收敛”、把 D5 描述为“已发生污染”。现网实测后两者均已修正：D4 实际形态是“对账把正确值改成错误值并停住”（收敛到错值，危害更隐密），D5 因字典 id 恰好等于 code 而尚未现形（属潜在耦合）。保留结构修法的理由不变：两条写入路径的口径分叉已被证实会产出 8,367 行错值。

## 3. 统一执行标准（四条不变量）

### I1 · 单一构建者

`crm_notice_search` 的业务内容列与指纹列**全部**只能由 `buildWideRow` → `upsertWideRows` 写入。对账与状态变更一律退化为「检测差异 → `syncWideIds(ids)`」。

- **无例外**：指纹列也走同一条 upsert 路径（与内容取自同一次 SELECT 快照，见 §4.1），因此 `src/lib/**` 下不存在任何对宽表的 UPDATE 语句。
- 强制：门禁 `scripts/check-wide-table-ssot.mjs` 扫 `src/lib/**`，出现 `UPDATE crm_notice_search` 即 fail（无白名单）。宽表的删除类写操作只允许 `DELETE`（ghost 清理与 `purgeNoticeSearch` 两处出口）。
- 现状违规：D4-D7 四处 UPDATE（`src/lib/db/migrations/032` 中的 UPDATE 属历史一次性收敛，门禁扫描范围不含 `db/migrations/`）。

### I2 · 口径常量化（禁止就地字面量）

| 口径 | 唯一出口 | 收编散点 |
|------|----------|----------|
| 描述源表达式 | `DESC_SOURCE_EXPR = "COALESCE(opp.description, n.description)"` | builder L27、`findSeoDetail` 子查询、翻译管道 3 处 `preferValue` |
| 截断长度 | `WIDE_LIMITS = { title:1000, description:2000, lockedTeaser:300, i18nTeaser:500, descriptionCn:500, bidOverview:200, reference:200, noticeId:100, beneficiary:300, unspscList:2000, rfqTitle:50, rfqTitleMin:10, rfqDescription:2000, rfqDescriptionMin:50 }`（`lockedTeaser` = SEO 详情页与列表未解锁摘要共用同一口径）| D13 四处 + `RfqWizard` L141/L145 与 API 双口径 |
| 译文来源标记 | `TRANSLATION_MODEL = { SAME_LANG:"same-lang-passthrough", EN_PIVOT:"en-pivot" }` | D6：废弃 `skip-same-lang`；D14：中枢兜底写 `EN_PIVOT` |
| 精选中文优先级 | 仅 `buildWideRow` 内实现 | D7 |
| 合格机会口径 | 已有 `qualifiedOppWhere`（`featured.ts` L15）——builder 内联的三条件 SQL 改为其派生 | builder L38/L55 与 featured.ts L17 双份 |

- 强制：同一门禁禁止上述文件出现裸 `slice(0, 2000)` / `LEFT(..., 2000)` / 字面量 `'skip-same-lang'` / 内联 `is_qualified = 1 OR status = 1 OR audit_status = 1`。
- 归属层：`src/lib/utils/`（repos 与 services 均可依赖，符合红线 1/4，避免 repos→services 反向依赖）。

### I3 · 状态转换必须成对同步

凡写 `rfq_status` 处，必须同时触发搜索侧动作：

- 转 `published` → `enqueue(pool, [id])`（500ms 去抖批量 → `syncWideIds`）
- 转 `draft/pending_review/rejected/closed` → `purgeNoticeSearch(pool, [id])`（删宽表行 **+ 删 Meili doc + `invalidateSearchCache`）

因审核由站外后台直接写库（红线 5 允许），事件驱动覆盖不到，必须有兜底对账：

- `reconcilePlatformStatus()`：用 `idx_entry_source` 取 `entry_source='platform'` 集合，与宽表存在性做集合差 → 应有而无 → `syncWideIds`；而无而应有 → `purgeNoticeSearch`。**这一条同时修掉 D1 与 D2**。

- 强制：门禁扫描「出现 `rfq_status =` 赋值但不 import 同步函数」的文件即 fail；写入 ARCHITECTURE.md 红线 #6。

### I4 · 编号命名空间落到 DB 结构（分两步，风险隔离）

`OSRFQ-{id:12}` 前缀保留（人类可读），但隔离保证改由 DB 承担。

- **步骤 A（本轮，零 DDL 风险）**：`daily-sync.cjs` 为平台行加列级保护——ODKU 子句中，平台归属列写成 `` col = IF(entry_source='platform', entry_source_col 原值, VALUES(col)) ``；并在每轮同步后输出「外部行与平台行撞唯一键」计数，>0 时告警退出码非 0。修 D9。
- **步骤 B（不进启动迁移）**：`crm_bid_notices` 增加 `uk_source_notice (entry_source, notice_id)`。现网该表 **401,026 行**，历史同类 ALTER 耗时 100 分钟且需处理 MDL 升级阻塞——因此**必须走停服离线窗口**（`pm2 stop` → `ALTER` → 校验 → `pm2 start`），并以运维 runbook 交付，不由 `runMigrations` 自动执行。
- **前置探测（硬要求）**：`uk_notice_tenant` / `uq_notice_source` 的**实际列组成不在本仓库定义**（属爬虫侧 CRM 表）。实施步骤 B 前必须 `SHOW INDEX FROM crm_bid_notices` 双侧（内网源库 + 线上目标库）取证，再决定新增还是替换；源/目标键定义不一致时先对齐源库，否则 ODKU 语义在两侧不对称。**本 spec 不预设其列组成。**

## 4. 设计

### 4.1 源指纹列（I1 的实现核心）

- 新文件 `src/lib/services/search-sync/wide-fingerprint.ts` 导出 `WIDE_FP_EXPR: string` —— 全库唯一的指纹 SQL 表达式（依赖别名 `n` / `opp`，与 `WIDE_OPP_JOIN` 同构，供多处拼接）：输入分量 = 主表内容列 + `DESC_SOURCE_EXPR` 描述 + 机会表展示列 + 桥接表/翻译表/candidates 三张输入表的 `COUNT + SUM(CRC32(...))` 聚合（**不用 GROUP_CONCAT**：其默认 1024 字节上限会漏检超限后的内容变化）。指纹与内容同快照写入，宽表无需任何 UPDATE；配套 `detectWideFingerprintDrift()` 以主键游标轮转只读检测。
- **指纹与内容同快照（关键设计点）**：`WIDE_SYNC_SELECT` 追加 `,<WIDE_FP_EXPR> AS sync_src_hash`，`buildWideRow` 原样透传，`upsertWideRows` 把它作为普通列一并写入。因此：
  - 宽表不需要任何 UPDATE（I1 绝对成立）；
  - 不存在「内容旧、指纹新」的掩蔽窗口 —— 若快照之后输入又变化，存盘指纹与**下一轮实时计算**的指纹必然不等，被对账再次捕获，收敛单调；
  - 迁移中途失败导致指纹未写 → 值为 `''` ≠ 实时指纹 → 下轮自动重建（自愈，无需人工干预）。
- 检测侧：`reconcileFingerprint()` 用同一 `WIDE_FP_EXPR` 在只读查询中实时计算，与 `ns.sync_src_hash` 比较，仅返回不等 id。
- 收敛性来源：指纹只依赖**输入**（主表/机会表/翻译表/桥接表/candidates），不依赖宽表当前值 ⇒ 修复后重算必然相等 ⇒ 第二轮对账返回空集，可被自动断言。
- 已知边界（明确文档化，不假装完美）：`crm_agency_aliases` 与 UNSPSC 字典树自身的变更**不进入指纹**（它们是全表级维度），依赖现有 10 分钟缓存 TTL + `requestIndexRebuild` 手动全量重建兜底。
- 扫描策略：`reconcileFingerprint()` 以宽表主键游标轮转切片（`WHERE id > :cursor ORDER BY id LIMIT 5000`，每轮 2 片）；游标为进程内状态，**重启后从 0 重新清扫**（可接受：全表一轮的成本上限即为上电后首个覆盖周期），每轮输出游标位置与命中数日志，便于核对覆盖率。

### 4.2 对账层收敛

`wide-row-reconcile.ts` 最终只保留三类函数，且**全部只返回 id、不改业务列**：

| 保留 | 处置 |
|------|------|
| `reconcileGhostRows` | 保留（含平台非 published 行清理），补 Meili doc 删除联动 |
| `reconcileFingerprint`（新） | 取代 `reconcileDeadlineSec` / `reconcileIsFeatured` / `reconcileTranslations` / `reconcilePreciseCodes` / `reconcileContentDrift` —— 五个函数与其 5 段 UPDATE SQL 一并删除，`sync-scheduler.ts` 定时器 2/3 的调用点同步改为单一指纹对账 |
| `reconcilePlatformStatus`（新） | 平台行可见性集合差（I3 兜底） |

`SUPPORTED_LANGS` / `WIDE_SYNC_SELECT` / `WIDE_SYNC_JOIN` 保持单一事实源地位不变。

### 4.3 可见性出口

- 新文件 `src/lib/services/search-visibility/purge.ts`：`purgeNoticeSearch(pool, ids)`（宽表 DELETE + Meili `deleteDocuments` + `invalidateSearchCache`），Meili 不健康时走 `requestIndexRebuild` + `enqueueRetry`，与现有级联失败语义一致（不静默丢弃）。
- 修 D1 根因：`syncNoticeIds` 的文档删除条件由「宽表+主表都缺」改为「宽表缺行 **且** 主表行不满足 `PLATFORM_PUBLISHED_ONLY`」；「主表存在但宽表缺行」仍交由对账修复（保持既有不误删原则）。

### 4.4 平台发布链路（I2/I3 落地）

- 新文件 `src/lib/services/notices/platform-rfq.service.ts` 收编全部 SQL 与校验：
  - `validateRfqPayload(body)`：标题 10–50 字，上限从现有 `WIDE_LIMITS.rfqTitle = 50` 导出（与 `RfqWizard` 校验同一常量，**消除现存的前端 50 / API 静默截断 50 双口径**），超限返回校验错误而非静默截断；描述 50–2000，与 `WIDE_LIMITS.description` 对齐（现 API 允许 5000 而前端限 2000，取严格一侧）；`category_l1_id/l2_id` 必须存在于 `crm_unspsc_codes` 且层级正确；`deadline` 按**北京时间** 23:59:59 折算（修 D15），展示与 `deadline_ts` 同口径；`status` 入参白名单只允许 `draft`（修 D11）。
  - `createPlatformRfq()`：INSERT 与 `reference/notice_id` 回填合并为**同一事务**（修 D12），`notice_id` 生成失败即整体回滚。
  - `transitionRfqStatus()`：状态机白名单复用 `RFQ_STATUS`，末尾成对调用 `enqueue` / `purgeNoticeSearch`（I3）。
- `src/app/api/rfq/**` 全部改为薄壳（鉴权 + 参数解析 + 委托），满足 D10。
- 平台 RFQ 分类入宽表（修 D8）：`buildWideRow` 的 UNSPSC 入参增加「主表 `category_l*_id` 直取」优先级——`unspsc = precise ?? legacy ?? platformCategory`，其中平台分类只填 `level1/level2`（与表单二级口径一致）。**不新增回写 `crm_bid_notice_unspsc_codes`**（该表由爬虫侧拥有，写它会造成双源）。

### 4.5 迁移 087（`087-wide-table-sync-fingerprint.ts`）

按「INSTANT 优先、重活不进启动路径」拆分：

1. `crm_notice_search` `ADD COLUMN sync_src_hash CHAR(32) NOT NULL DEFAULT '' AFTER updated_at` —— MySQL 8.0 实例级 INSTANT ADD COLUMN，元数据变更（现网已确认 8.0.29+，参照 028/030 同类判断）。
2. 宽表脏数据一次性纠偏（**现网实测命中 0 行，保留作防御性措施** —— 字典 id 与 code 脱钩时会立即产生原码污染）：`UPDATE crm_notice_search SET precise_levelN='' WHERE precise_levelN REGEXP '[^0-9,]'`（清 D5 被写入的原码；清空后由构建路径按 ID 重新填回，比“猜测映射”安全）；`sync_src_hash=''` 作为待刷新标记，由对账/回填自然收敛。
3. 平台行编号补齐：`entry_source='platform' AND (notice_id IS NULL OR notice_id='')` → `OSRFQ-{id:12}`（覆盖 D12 已产生的历史失败行）。
4. 注册到 `src/lib/db/schema.ts`：新增 `m087` import、加入 `ALL_MIGRATIONS`、更新头部注释清单。
5. **不做**：任何 `crm_bid_notices` 的加列/加索引（见 I4 步骤 B）。

回填策略：不在迁移内做长事务。首帧刷新走既有 sanctioned 路径 —— 停服 → `TRUNCATE TABLE crm_notice_search`（保留结构与索引，由新构建逻辑自动重建）→ 启服 → `fullBackfill`。迁移内只登记 `sync_src_hash` 默认空值，避免与在线流量争抢 MDL。

### 4.7 翻译管道（I2 收口）

- `TRANSLATION_MODEL` 常量落地，builder 判定改 `SAME_LANG`（修 D6）。
- `upsertEnPivotTranslation` 补写 `model = EN_PIVOT`（修 D14）。
- 精选 `description_cn` 直出与 `same-lang` 原文回填的优先级仅存在于 `buildWideRow`；`reconcileTranslations` 删除后其覆盖行为自然消失（修 D7）。
- 维持「AI/翻译均为手动按需触发」的既有实践，不引入发布即自动全量翻译。

## 6. 验收判据

单测（`tests/unit/lib/services/search-sync/`、`tests/unit/lib/services/notices/`）：

1. `buildWideRow` 确定性：同一 raw 输入两次调用输出深度相等。
2. 描述优先级：精选 + `description_cn` 存在 → `description_zh = description_cn`；无译文且 `model=SAME_LANG` → 对应语言列回填原文（D6 回归）。
3. `model` 枚举：`SAME_LANG` / `EN_PIVOT` / provider 名三分支判定。
4. 平台分类入宽表：`category_l1_id/l2_id` 存在时 `unspsc_level1/2` 非空（D8）。
5. `validateRfqPayload`：标题/描述超限报错而非截断、`status='published'` 被拒、非法 `category_id` 被拒、deadline 按北京时间折算（D11/D12/D15）。
6. 门禁自测：构造含 `UPDATE crm_notice_search` 的夹具文件应被 `check-wide-table-ssot.mjs` 判 fail。

集成（`tests/integration/`，走 `seed-test-db`）：

7. **收敛性断言**：`reconcileFingerprint` + `reconcilePlatformStatus` 连跑两轮，第二轮返回 `ids.length === 0`。
8. 精选公告（有合格机会且描述不同）经一次对账后 `description` 仍等于 `COALESCE(opp.description, n.description)`（D4 反例回归）。
9. `precise_level1` 经对账后仍全为数字/逗号（D5 回归）。
10. 平台 RFQ：`published` → 宽表有行且 Meili 有 doc；`closed` → 宽表无行**且 Meili 无 doc**（D1/D2 端到端）。

门禁：`wide-row-builder.ts` / `wide-row-reconcile.ts` / `wide-fingerprint.ts` / `platform-rfq.service.ts` 加入 `vitest.config.ts coverage.include`，`npm run test:ci` 维持语句 ≥90% / 分支 ≥85%。

生产核对 SQL（人工，一次性；结果归档到 `docs/reviews/`，供 Slice 0/1 上线后对比）：

11. `SELECT COUNT(*) FROM crm_notice_search WHERE precise_level1 REGEXP '[^0-9,]'` → 0。
12. `SELECT COUNT(*) FROM crm_notice_search ns LEFT JOIN crm_bid_notices n ON n.id=ns.id WHERE n.id IS NULL OR (n.entry_source='platform' AND IFNULL(n.rfq_status,'')<>'published')` → 0。
13. Meili doc 数 == 宽表行数（`getWideTableCount` vs `numberOfDocuments`）。
14. `SELECT COUNT(*) FROM crm_bid_notices WHERE entry_source='platform' AND (notice_id IS NULL OR notice_id='')` → 0；`... AND notice_id LIKE 'RFQ-%'` → 0。

## 7. 非目标与后续项

- **Outbox/CDC**（路线 3）：彻底摆脱 `id > watermark` 假设，但要求站外审核后台改为写事件表，跨系统协调成本与本轮收益不匹配。若后续出现「对账延迟导致业务事故」的真实案例，再启用，届时本 spec 的 `reconcilePlatformStatus` 由 outbox 消费取代。
- **I4 步骤 B（`uk_source_notice`）**：交付为停服窗口 runbook + 双侧索引探测清单，不进入代码启动路径。
- **API 响应信封统一 / 平台公告自动全量翻译**：各自独立议题。
- `crm_notice_search.id` 仍是 `INT UNSIGNED`（现网主表 id 已 ~1.78e9，上限 4.29e9）：本轮只记录为容量观察项，不改类型。

## 8. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 删除 5 个对账函数后漏掉某种不一致 | 指纹表达式逐项覆盖五者的输入字段；集成判据 7 强制第二轮零变更；`reconcileDeadlineSec` 的 `GREATEST(COALESCE(...,0),0)` 负值保护并入指纹表达式与 builder |
| 输入在 SELECT 快照后继续变化，内容短暂陈旧 | 指纹与内容同快照 ⇒ 存盘指纹必定与下一轮实时值不等，被再次捕获；叠加游标轮转，全表覆盖周期封顶（§4.1） |
| 站外后台在窗口期直接改 `rfq_status` | `reconcilePlatformStatus` 每轮兜底；Meili 不可用时 `enqueueRetry` + `requestIndexRebuild`，不静默丢弃 |
| TRUNCATE 重建期间搜索命中率下降 | 沿用既有 `isWideTableReady` 就绪门 + API 优先 30 秒窗口，停服窗口内执行 |
| 宽表加列非 INSTANT（版本低于预期） | 迁移前用 `INFORMATION_SCHEMA` 探测并打印 `SHOW INDEX`/版本；若不支持则退化为「离线窗口 ALTER」，与 I4 步骤 B 同批执行 |
| 指纹查询拖慢 5 分钟对账 | 游标轮转切片（每轮 2×5000 行）+ 只读聚合子查询，与既有对账负载同量级 |
| `daily-sync` 列保护改动引入回归 | 变更限定在 ODKU 子句生成；同步后撞键计数 >0 显式告警；`--once` 模式先跑冷/热两轮回归（`logs/regression-result-*.json` 同路径） |
