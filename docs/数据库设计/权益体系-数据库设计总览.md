# 权益体系 — 数据库设计总览

> 事实源：`docs/OS_NEO_SMART_2026官网正式价格体系_V1.0.docx`（六档主套餐矩阵 + 增值服务目录 + API 授权）。
> 本体系为**全新表组**，不映射、不兼容、不双写旧表（`crm_membership_plans` / `crm_user_subscriptions` / `crm_user_entitlements`）；
> 切换验收后旧表整体下线。结构变更遵循 `docs/adr/0003-shadow-table-blue-green-migration.md`（影子表蓝绿·两阶段人工闸口）。
> 表名不带年份/代号后缀（正式名即终态名），每张表均带表级 `COMMENT` 说明用途；建表与列注释以 `src/lib/db/migrations/092-benefit-system-tables.ts` 为唯一事实源。

---

## 1. 设计原则：1 就是 1，2 就是 2

| 旧体系的含糊点 | 新体系的精确表达 |
|---|---|
| 「不限」= `unlock_quota=99999` 魔法数字 | 额度列以 **`-1` 显式表示不限**，等值判断即语义本身 |
| 权益只有布尔 + `benefit_rank >= 阈值` 推导 | 矩阵**一行一格一个整数**，每格直接存该档该权益的精确值 |
| 「基础/企业级/API/可配置」多值权益无法落库 | 枚举型权益统一**层级字典**（0-4 严格递增），逐档逐列定义见各表文档 |
| 「建议账号数」无执行口径 | 席位为独立实体：套餐存 `seat_limit`（-1=不限），成员关系落表 |
| 增值服务只有留资、无价格形态 | 服务目录承载**计价形态**（per_unit/per_time/per_year/token/project/quote/contact） |

## 2. 数值语义字典（全库统一）

- **枚举型权益值（`value_level INT`）**：**0 恒表示「无」**（docx 的 `—`），正整数从 1 起按该行 docx 出现顺序递增；
  **不存在全局统一的层级表**（同一个 `2` 在 `advanced_keyword_search` 是「✓」、在 `ai_match` 也是「✓」、在 `unspsc_cpv` 还是「✓」，但 `history_notice_db` 的 `1` 就已经是「✓」）。
- **枚举行层级字典（`level_dict` JSON）的文本 = 价格体系文档单元格原文逐字**（`"—"`/`"✓"`/`"基础"`/`"企业级"`/`"可配置"`/`"配额/优惠"`…），
  整数只负责把这行原文定序，**不允许出现设计侧自行改写的词**——这样矩阵里的数字与库内文本可双向核对。
  数据库层面只保证单调性可比较，各权益每级的含义只在本权益自己的 `crm_benefit_catalog.level_dict` 内成立。
- **额度型权益值（`value_num INT`）**：正数=条数/次数；`-1`=**显式不限**（全库唯一的不限表达）；`0`=该档明确无额度（如普通用户免费解锁 0 条、`tech_support` 非套餐权益），属已裁决事实而非未配置。
- **金额型权益值（`value_amount DECIMAL`）**：`0.00`=会员免费/包含；正数=会员价；NULL 在本矩阵列出现即违反 CHECK（矩阵格必须显式有值）。
- **布尔型权益值（`value_level INT`）**：仅允许 `0/1`，由服务层按 `value_kind` 校验（CHECK 不做逐类型约束，避免迁移期锁表改约束）。

### 2.1 已实测发现的两个 MySQL 语义坑（建表阶段已修正，新增列时必须避开）

| 坑 | 现象 | 本表组的写法 |
|---|---|---|
| CHECK 中引用**可空列**的比较式（如 `col > 0`） | NULL 时表达式为 UNKNOWN，MySQL **视为通过**，约束形同虚设 | 比较必须先写 `col IS NOT NULL AND ...`（见 `chk_price_by_mode`） |
| `NOT NULL ENUM` 不写 DEFAULT | 隐式默认值 = **首个枚举成员**，漏传不报错而是静默写入错误状态 | “必须显式传入”的状态/快照列改用 `VARCHAR + CHECK 取值域`（见订单表 `status`/`sale_mode_snapshot`） |

> 两条均由 092 迁移的**约束活性验证**（本地库事务内插入 + 回滚）跑出来后修正，并由单元测试固化断言防回归。
> 区分：“只约束取值域、允许默认值”的列（如各表 `status DEFAULT 'active'`）继续用 ENUM 没问题。

## 3. 表清单与实体关系

```
crm_benefit_catalog（权益目录：有哪些权益、值什么类型）
        │ 1
        │
        │ N                N                1
crm_plan_benefits（矩阵：plan_code × benefit_code → 精确值）
        │ N
        │ 1
crm_plan_catalog（六档套餐：价格、有效期、席位）
        │ 1
        ├────────────┐
        │ N          │ N
crm_plan_subscriptions（套餐订阅：购买快照）
        │ 1          │ 1
        ├────────────┼─────────────┐
        │ N          │ N           │ N
```

## 4. 门控读取口径（供服务层，不落结构）

- 某用户某权益的精确值 = `订阅(plan_code) JOIN 矩阵(plan_code, benefit_code)`，**运行时不缓存档位推导链**；
- 消耗型权益一律走 `crm_benefit_quotas` 的 `FOR UPDATE` 行锁扣减（沿用 unlock-quota 单口径纪律，但记账表为新表）；
- 席位权益归属：成员操作按 `seat → subscription` 解析，额度池默认**订阅级共享**（`scope='subscription'`），席位独立额度用 `scope='seat'` 行表达。

## 5. 裁决记录与残留待裁决项

1. **免费档（已定稿 2026-09-22）**：免费档=**普通用户权益**——`crm_plan_catalog` 保留 `plan_code='free'`（price=0）作为矩阵取值列，但**不建订阅、不进官网六卡**；普通用户仅享有目录表 `requires_subscription=0` 的权益行，计量型（如免费标讯额度）落 `crm_benefit_quotas` 的 `subscription_id=NULL` 普通用户池（对比旧体系：解锁流水 COUNT 终身累计 → 新体系周期账本）。
2. **含税口径（已仲裁 2026-09-23，迁移 093）**：文档 09 章未定；`price_incl_tax` 列语义位（0=未税/1=含税/NULL=未定），付款页定稿前恒 NULL。
   仲裁缘由：旧**列注释**写「NULL=未定；未定前禁止开单」，而本条把「定稿前恒 NULL」定为计划状态——实库 7 行该列全 NULL，照注释执行则**没有任何一档可自助成交**。两条互斥必须仲裁而非绕过，结果以本决策记录为准：093 将注释改为「NULL 期间本表价格仅作报价参考、不得开票，不阻止自助成交」——开票限制属财务与发票系统的闸门，不由商品目录的一列注释充当；履约层随之撤销原来每单一条的口径冲突异常（不改代码就会留下一句引用已失效注释的假报警）。
   ⚠ 实施记录（可复用的 MySQL 语义）：改列注释在 MySQL 8.0 **没有 INSTANT/INPLACE 路径**——先钉 `ALGORITHM=INPLACE` 被 `ER_ALTER_OPERATION_NOT_SUPPORTED: Try ALGORITHM=COPY` 直接打回，只能 `ALGORITHM=COPY, LOCK=SHARED` 重建。本表仅 7 行且无应用写入方，重建毫秒级；回读已验列定义/索引/CHECK/表注释与 7 行数据均未变。错把它归为“元数据级变更”正是本次被数据库纠正的认知。
3. **席位额度口径（待裁决）**：订阅共享还是席位独立（`scope` 两值结构都成立，需服务层定一个默认）。
4. **目录数据已入库（2026-09-22 首次录入，2026-09-23 补两行免费权益）**：docx 02/03/04/05/07 章的静态目录已**直接写入 4 张静态表**（20 权益 / 7 套餐 / 140 矩阵格 / 15 服务），
   事实表（订阅/额度/席位/订单）保持空表——不做存量回填、不做双写，线上读写路径零变化。
   不来自 docx 02 章矩阵的补充共四处，均已在表内逐格留 `note_zh` 标明出处与是否逐字：
   - `tech_support`、`procurement_consult` 两行不在 02 章矩阵内，但服务目录 `grant_benefit_code` 外键与「ADVISOR 每月 1 次咨询」需要它们成为权益行（故全档显式存 0，ADVISOR 的 `procurement_consult`=12）；
   - ENTERPRISE 的「标讯权益」docx 原文是「API/批量数据」（不是一个数），该行存 `-1` + 格级原文注，是唯一一格整数不等于原文语义的取值；
   - 各档「会员优惠」docx 未给折扣数值，故 `ai_tender_analysis` 用枚举存原文，`value_amount` 列本轮无数据（不编造折扣率）；
   - **docx 表 2 没有普通用户列**，xlsx 报价表的「免费注册体验」行只列两项——`ai_summary`「采购摘要」与 `similar_opportunity`「相似机会推荐」。这两项线上一直在交付（旧代码的 `summary`/`similar` 门控），矩阵里却没落点，2026-09-23 补为新权益行：`ai_summary` 枚举 `1=部分脱敏 / 2=完整`（免费档取 1，为 xlsx 逐字；六付费档取 2，**推读**自「部分脱敏」限定仅出现在免费行），`similar_opportunity` 全档 L1（免费档 xlsx 逐字，向上延伸依据「高层包含低层」不变式）。`free.global_search`=L1 也是**推读**（两份文档均未写给免费档，沿用线上既有行为），已在格上标注。

## 6. 旧体系现状盘点（2026-09-22 实库 SHOW CREATE 核实，作为新设计的对照依据）

| 旧表现状 | 对新设计的影响 |
|---|---|
| `crm_membership_plans`：5 行在用（free + 四档 129/999/1299/8800，后两档 99999 冒充不限） | free 行同位保留为普通用户矩阵列；99999 → `-1` 显式不限 |
| 普通用户当前实际权益 = rank 0 门控（脱敏摘要/相似机会）；**免费解锁额度已被 migration 058 主动置 0**（`free_quota=0`），free 行 `unlock_quota=3` 为无人读取的死列（`getFreeQuota()` 只读 `free_quota`） | “普通用户权益”在新体系是**矩阵 free 列的显式取值**，不再靠“rank 0 + 额度 0”双重隐含；列语义漂移（同名列有的有人读有的没人读）在新体系由“矩阵单列”消灭 |
| 免费/付费解锁用量均 = `COUNT(crm_opportunity_unlocks)` 流水累计，终身口径不可重置 | 新体系普通用户池 `period` 支持月度/年度重置；解锁流水表仍保留作审计，不再充当场账 |
| `crm_user_subscriptions`：`user_id NULL + user_key` 双轨、无订单号/价格快照 | 新订阅表单轨非空 + `source_order_no NOT NULL` + `price_paid` |
| `crm_user_entitlements`：`is_upgraded` 布尔位、`quota_total=99999`、单一解锁额度 | 新体系 `replaced_by_id` 指针 + 多权益分池 |
| `crm_users.membership_tier`（'free'/'vip'）+ 到期降级定时任务/退款降级 SQL 直写 | 新体系不再维护布尔式 tier 列：会员身份 = “有无 active 订阅行”单一事实，降级链路由订阅状态自然产生，无需直写用户表 |
| `crm_quota_addon`/`crm_quota_alert`：tenant 维度旧表，与会员体系无关 | 不纳新、不迁移，旧表下线时单独评估 |
