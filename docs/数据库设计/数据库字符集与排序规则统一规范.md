# 数据库字符集与排序规则统一规范

> 适用范围：supply-os 全部 MySQL 表、连接、DDL 与迁移脚本。
> 目标：全栈单一编码 UTF-8（数据库 `utf8mb4`），库内排序规则统一，杜绝 `Illegal mix of collations`。
> 关联：源码级编码约定见 `docs/i18n-encoding-standard.md`；结构变更流程见 `docs/adr/0003-shadow-table-blue-green-migration.md`；影子表脚本 `scripts/shadow-password-resets-phase1.ts` / `phase2.ts`。
> 数据实况来源：`scripts/tmp-charset-audit.mjs`（只读审计，2026-09-22 于 dev 库 `crm`）。

---

## 1. 核心规范（强制）

| 维度 | 强制标准 | 说明 |
|---|---|---|
| 存储引擎 | **`InnoDB`** | 唯一允许引擎；不支持事务/行锁的引擎禁止使用。 |
| 字符集 | **`utf8mb4`** | 完整 4 字节 UTF-8，可存中文/emoji/生僻字。**禁止 `utf8mb3`（旧 `utf8`）**——它只有 3 字节，存不下 emoji 与部分汉字扩展。 |
| 排序规则（默认） | **`utf8mb4_0900_ai_ci`** | MySQL 8.0 的 Unicode 9.0 算法，`ai`=不区分重音、`ci`=不区分大小写；性能与 Unicode 合规性最佳。全库文本列统一此值。 |
| 排序规则（例外） | `utf8mb4_bin` | **仅限**需要精确字节匹配、区分大小写的列：license key、哈希摘要、UNSPSC 码值等。使用必须在对应表设计文档中标注"有意为之"。除此之外禁止其它 collation。 |

**铁律**：
- 任何 `CREATE TABLE` 必须**同时显式声明** `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`，**绝不依赖库/表默认继承**（见 §5 案例一：库默认曾为 `utf8mb4_unicode_ci`，漏写即产出错误表）。
- 禁止在列级随意写与表级不同的 collation；确需 `utf8mb4_bin` 的列单独声明并注明原因。
- 例外白名单（当前）：`crm_contact_unlocks`、`crm_unspsc_codes`、`gcollector_license_keys`、`industry_write_log` 使用 `utf8mb4_bin`。

## 2. 连接池配置标准（强制）

连接层字符集**必须显式声明 `utf8mb4`**，不依赖 mysql2 驱动默认值，否则 emoji/部分汉字在写入或读取时损坏。

```ts
// src/lib/db/pool.ts（现状，已合规）
const pool = mysql2.createPool({
  host, port, user, password, database,
  charset: "utf8mb4",        // ← 红线：显式声明，勿删勿改
  connectionLimit: Number(process.env.DB_POOL_LIMIT || 20),
  waitForConnections: true,
  enableKeepAlive: true,
  // ...
});
```

要求：
- **所有**建池/建连入口一律带 `charset: "utf8mb4"`：`src/lib/db/pool.ts`、`scripts/daily-sync.cjs`、`scripts/crawl-awards/db.ts`，以及任何一次性脚本（如 `scripts/tmp-charset-audit.mjs`、影子表脚本）。
- 影子/审计脚本用 `mysql2.createPool({ ..., charset: "utf8mb4" })`，与主池一致。
- 出站/跨库连接同样必须显式 `charset: "utf8mb4"`。
- `dateStrings` 等其它连接参数属独立议题（遗留待办），**不得与本规范的编码改动同批引入**。

## 3. DDL 建表模板

新建表以此模板为准（含完整列定义与约束示例）：

```sql
CREATE TABLE IF NOT EXISTS `example_table` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id`     BIGINT UNSIGNED NULL                    COMMENT '关联 crm_users.id；无账号场景可空，事后回填',
  `code`        VARCHAR(128)    NOT NULL                COMMENT 'SHA-256 哈希，不存明文',
  `code_type`   VARCHAR(20)     NOT NULL DEFAULT 'default' COMMENT '场景枚举（见列注释/表文档）',
  `name`        VARCHAR(190)    NOT NULL                COMMENT '普通文本列，继承表级 0900_ai_ci',
  `token_hash`  CHAR(64)        CHARACTER SET utf8mb4 COLLATE utf8mb4_bin
                                NOT NULL                COMMENT '例外：精确匹配列，显式 bin 并在此注明原因',
  `is_active`   TINYINT(1)      NOT NULL DEFAULT 0      COMMENT '布尔用 TINYINT(1)',
  `amount`      DECIMAL(14,2)   NOT NULL DEFAULT 0.00   COMMENT '金额禁用 FLOAT/DOUBLE，用 DECIMAL',
  `expires_at`  DATETIME        NULL                    COMMENT '时间统一 DATETIME',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`  DATETIME        NULL DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_token` (`token_hash`),
  KEY `idx_user_type` (`user_id`, `code_type`),
  CONSTRAINT `fk_example_user` FOREIGN KEY (`user_id`) REFERENCES `crm_users` (`id`)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;   -- ← 引擎/字符集/排序规则三者必须显式齐全
```

要点：
- 表尾 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci` **不可省略 COLLATE**。
- 例外列（`utf8mb4_bin`）在列定义内显式声明 `CHARACTER SET ... COLLATE ...` 并写注释。
- 金额用 `DECIMAL`，布尔用 `TINYINT(1)`，时间用 `DATETIME`，主键用 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 迁移内 DDL 若含 `ALGORITHM` 选项，注意与前一子句之间**必须有逗号**（见 §5 案例三）。

## 4. 历史遗留问题治理策略

审计实况（dev 库 `crm`，共约 161 张基表）：

| 表级 collation | 数量 | 定性 | 处置 |
|---|---|---|---|
| `utf8mb4_0900_ai_ci` | 124 | ✅ 合规 | 保持 |
| `utf8mb3_general_ci` | 18 | ❌ 3 字节 + 错序 | 先甄别是否仍被使用：老 CMS 遗留表（`system`/`page`/`product`/`message`/`plugin`/`link`/`picture`/`oauth`/`field`/`posid`/`region`/`donation`/`download`/`crm_client_hangye`/`crm_client_order`/`crm_comment`/`crm_reply`/`crm_file_cleanup_log`）**优先纳入精简删除**；确需保留者 `CONVERT` 到 utf8mb4/0900_ai_ci |
| `utf8mb4_unicode_ci` | 15 | ⚠️ 字符集对、排序错 | `CONVERT TO ... 0900_ai_ci`（含 `training_*`、`crm_opportunities`、`crm_knowledge_base`、`flyway_schema_history`、`*_backup_*`） |
| `utf8mb4_bin` | 4 | ✅ 有意例外 | 保持并登记 |

**根因**：库默认为 `utf8mb4_unicode_ci`，且历史建表普遍漏写 `COLLATE`。治理按序：

1. **改库默认**（元数据操作，瞬时，不动存量表）：
   ```sql
   ALTER DATABASE `crm` CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   ```
   此后"漏写 COLLATE"不再静默产出错误表（但仍要求显式声明）。
2. **甄别 + 删除遗留表**：对 18 张 utf8mb3 老表，先查代码引用；无引用者按"精简"删除（走影子/备份，可回滚）。
3. **逐表 CONVERT**：需保留的 unicode_ci / utf8mb3 表：
   ```sql
   ALTER TABLE `t` CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   ```
   - `CONVERT TO` 为**整表重建**：小表秒级、放低峰；大表按 `docs/adr/0003` 走**影子表蓝绿切换**。
   - 已有先例：迁移 065 对 `crm_refresh_tokens`/`learning_orders`/`training_orders` 整表 CONVERT 到 0900_ai_ci，修复 `backfillUserIds` 的 `Illegal mix of collations`；迁移 066 将各业务表 `user_key` 列 `MODIFY ... COLLATE utf8mb4_0900_ai_ci`。
4. **例外登记**：`utf8mb4_bin` 表保留，在对应表设计文档标注用途。
5. **加门禁防回潮**（§5 案例一的根治）：新增 lint 脚本扫描迁移/DDL 中的 `CREATE TABLE`，凡 `DEFAULT CHARSET=utf8mb4` 未紧跟 `COLLATE=utf8mb4_0900_ai_ci` 且非 bin 例外者 fail，纳入 `npm run lint` / CI（与 `check-mojibake`、`check-wide-ssot` 同族）。

> 所有 CONVERT / DROP 属结构变更，遵循"两阶段·人工闸口"，脚本产出 SQL 后由人工在低峰/停应用窗口执行，不并入启动自动迁移。

## 5. 常见错误案例与规避指南

**案例一：漏写 COLLATE，继承错误的库默认**
- 现象：`CREATE TABLE ... DEFAULT CHARSET=utf8mb4`（无 COLLATE），在库默认 `utf8mb4_unicode_ci` 下建出 unicode_ci 表；与 `crm_users`（0900_ai_ci）`JOIN`/比较时抛 `Illegal mix of collations`，回填或查询中断。
- 规避：建表**永远显式写全** `CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`；并改库默认兜底（§4 步骤 1）。
- 真实教训：影子表脚本 `shadow-password-resets-phase1.ts` 初版即漏写 COLLATE，已修正。

**案例二：用 utf8mb3（旧 utf8）**
- 现象：emoji / 4 字节字符写入报 `Incorrect string value` 或被截断。
- 规避：一律 `utf8mb4`；存量 utf8mb3 表 CONVERT 或删除。

**案例三：`ALGORITHM=INSTANT` 前缺逗号**
- 现象：`... COMMENT '' ALGORITHM=INSTANT` 直接 syntax error；该 DDL 在启动必跑阶段，一条逗号即可让**整个服务起不来**。
- 规避：`ALGORITHM` 是 alter_option 列表项，与前一子句间**必须有逗号**；迁移 DDL 先在真库临时小表验证语法。

**案例四：不钉 ALGORITHM 导致静默降级持锁**
- 现象：`ALTER` 不带 `ALGORITHM` 时，MySQL 可能判定不适用 INSTANT 而**静默回退 COPY**，持 `SHARED_NO_WRITE`，使在线写入排队等元数据锁（实测曾致写入口停摆 22 分钟）。
- 规避：显式 `ALGORITHM=INSTANT`（带逗号）+ `SET SESSION lock_wait_timeout = 5`，"不适用"时立即报错而非降级持锁；报错只转述数据库原始错误并给停服窗口指引。

**案例五：连接层未显式 charset**
- 现象：驱动默认非 utf8mb4 时，写入/读取中文或 emoji 乱码。
- 规避：所有 `createPool`/`createConnection` 显式 `charset: "utf8mb4"`（§2）。

**案例六：RENAME 切换误以为无锁**
- 现象：`RENAME TABLE` 是元数据操作但需**排他 MDL**；停应用不等于锁已释放，未结束事务仍会阻塞切换。
- 规避：低峰或短暂停应用执行，配短 `lock_wait_timeout` 快速失败；依据 `performance_schema.metadata_locks` 的 GRANTED/PENDING 判断，而非仅看进程名。
